# Additional Dataset Suitability Audit

Documentation audit: 2026-10-21. Recommendations concern scientific suitability, never anticipated method rankings. No raw candidate dataset was downloaded or evaluated. Reported fleet size is not a count of eligible continuous application histories. Raw continuity must be established before selection/execution. No candidate supplies edge deployment evidence by itself.

## Ranked recommendation

1. **Preferred: Google ClusterData 2019**, subject to a bounded, outcome-blind continuity and extraction audit. Month-long coverage, both resources, five-minute windows, eight independent production cells and a clear CC-BY-4.0 release make it the strongest documented match. Prefer long-lived alloc/application instances; freeze entity identity, restart/migration handling and resource denominators before acquisition. BigQuery scale is its main practical disadvantage.
2. **Optional third corpus: Alibaba Cluster Trace 2018**, particularly long-running containers, subject to denominator/cadence and release-terms verification. Adds a different operator, co-located service/batch environment and container entity type. Eight days support a 24h horizon but provide much less bootstrap/streaming diversity than a month. Machine-level traces are a separate entity-level robustness question, not interchangeable application replication.
3. **Defer Azure 2017/2019 for joint CPU/memory replication**: memory capacity metadata is not a memory utilization series. A later explicitly CPU-only replication is legitimate but cannot establish two-resource generalization.
4. **Defer newer Alibaba GPU releases** for this unchanged five-minute CPU/memory protocol. Newness, hardware diversity and size do not compensate for lifetime aggregates or hourly sampling.

This is a documentation-based ranking, not a final acquisition decision. No candidate is eligible for a claim until a reproducible, outcome-independent data suitability report passes. Do not bulk-download before scope/cost/terms are resolved.

## Stronger/newer alternatives checked

- **Alibaba GPU 2020**: two months, ~1,800 heterogeneous machines / >6,500 GPUs; Docker training/inference jobs, CPU percent-of-cores and main memory GB. However official `pai_sensor_table` averages over an instance lifetime, and machine metrics are also instance-associated aggregates. These are not five-minute utilization histories. Seven compressed tables total roughly 1.4GB from documented individual sizes; published hashes support acquisition reproducibility. Terms require clarification as for other Alibaba releases. Reject for current forecasting replication despite attractive diversity. [Official schema](https://github.com/alibaba/clusterdata/tree/master/cluster-trace-gpu-v2020).
- **Alibaba GPU 2026 (ASI)**: 185 relative days, up to 155,410 GPUs / 37,707 servers; pod/server topology and heterogeneous workload categories. CPU is request-normalized; memory is reported as average memory utilization, with denominator clarification still needed. **Hourly public facts cannot establish five-minute dynamics**. Pod archive alone is 351,803,513,445 bytes; three other archives add ~4.47GB. Stable hashed IDs but workload IDs can be null. Strong future heterogeneity candidate under a separately versioned hourly protocol, not a replacement made by upsampling. No general root licence found in this check; clarify terms and per-pod continuity first. [Official schema](https://github.com/alibaba/clusterdata/blob/master/cluster-trace-gpu-v2026/docs/schema.md), [download sizes](https://github.com/alibaba/clusterdata/blob/master/cluster-trace-gpu-v2026/docs/data_download.md).
- **Alibaba microservices 2021**: twelve-hour coverage cannot support an observed 24h future horizon; reject for this protocol, even though service latency/call dependencies are relevant to other system questions. [Official index](https://github.com/alibaba/clusterdata).

## Acquisition/adaptation gates

Before any candidate run, freeze: release/schema/version hashes; licence/attribution and export permission; stable entity key; observation statistic and resource denominator; interval measurement/availability timestamps; deterministic five-minute binning if valid; no upsampling or gap filling; finite/presence and continuous-history counts; duration and survival bias; bootstrap/stream eligibility; full 24h ground-truth density; random selection independent of outcomes; bounded export budget and hardware/storage plan. Distinguish cloud workload generalization, container evidence and hardware heterogeneity from actual cloud-edge deployment. No performance expectation is an inclusion criterion.
